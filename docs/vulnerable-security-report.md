# SwiftGov 有漏洞版本安全说明（Vulnerable）

## 1. 文档目的
本文档用于说明 `vulnerable` 版本中当前已知的主要安全漏洞，便于课程演示、漏洞复现与后续 `secure` 版本修复对照。

## 2. 影响范围
- 后端：`vulnerable/backend/app/main.py`
- 前端：`vulnerable/frontend/src/*`
- 数据：`vulnerable/backend/swiftgov_vulnerable.db`

## 3. 漏洞清单

### 漏洞 A：明文密码存储（高危）
- 位置：`/api/auth/register`、`/api/auth/login` 相关逻辑
- 现象：用户密码直接写入数据库 `users.password`，未进行哈希加密。
- 风险：数据库泄漏时，所有账号密码直接暴露，可撞库复用。
- 修复建议：
  - 使用 `bcrypt/argon2` 做单向哈希存储。
  - 登录时用哈希比对，禁止明文比对。

### 漏洞 B：弱令牌设计（高危）
- 位置：`current_user()` 鉴权逻辑（Bearer token 直接使用用户 ID）
- 现象：令牌本质是纯数字用户 ID（如 `Bearer 1`），无签名、无过期、无防篡改。
- 风险：
  - 可伪造 token 越权访问。
  - 攻击者可枚举 ID 进行横向访问与提权。
- 修复建议：
  - 使用 JWT（签名 + 过期时间 + 发行者）。
  - 服务端增加 token 黑名单/刷新机制。

### 漏洞 C：默认弱口令账号（高危）
- 位置：`seed.py`（默认 `admin/admin123`、`resident001/123456`）
- 现象：存在固定演示账号与弱密码。
- 风险：部署到公网后容易被暴力破解或字典攻击。
- 修复建议：
  - 首次启动强制改密。
  - 禁用默认账号或随机初始化密码。

### 漏洞 D：CORS 过宽配置（中危）
- 位置：FastAPI CORS 中间件配置
- 现象：`allow_origins=["*"]` 且允许所有方法/头。
- 风险：跨域调用面过大，增加接口被恶意站点滥用风险。
- 修复建议：
  - 仅允许受信任前端域名。
  - 按环境区分开发/生产 CORS 白名单。

### 漏洞 E：缺乏请求限流与防爆破（中危）
- 位置：登录、注册、密码修改等接口
- 现象：未做 IP/账号维度限流，也无验证码。
- 风险：可被持续尝试密码或批量撞库。
- 修复建议：
  - 增加限流（如每分钟请求次数限制）。
  - 登录失败累计触发验证码或临时锁定。

### 漏洞 F：输入校验与业务校验不足（中危）
- 位置：多处表单接口（注册、申请、公告等）
- 现象：仅做基础字段校验，缺少长度、格式、敏感字符、业务状态等更严格约束。
- 风险：脏数据写入、异常数据触发业务混乱，潜在注入与滥用风险增大。
- 修复建议：
  - 强化 Pydantic 规则（长度/正则/枚举）。
  - 服务端统一参数校验与错误处理。

### 漏洞 G：文件上传仅元数据模拟、缺乏安全检查（中危）
- 位置：申请材料相关逻辑（`Material` 仅记录文件名/大小）
- 现象：未做真实文件类型、内容扫描、大小与扩展名白名单控制。
- 风险：若后续接入真实上传，可能引入恶意文件上传风险。
- 修复建议：
  - 接入真实上传时做 MIME/扩展名校验、病毒扫描、对象存储隔离。
  - 下载与预览时做访问控制和安全头。

## 4. 典型复现示例（教学用途）

### 复现 1：伪造管理员令牌
1. 已知管理员常见 ID（例如 1）。
2. 构造请求头：`Authorization: Bearer 1`
3. 请求管理员接口（如用户管理接口）。
4. 若返回成功，则说明存在令牌伪造风险。

### 复现 2：明文密码可读
1. 打开 SQLite 数据库。
2. 查询 `users` 表的 `password` 字段。
3. 可直接看到明文密码。

## 5. 总结
当前 `vulnerable` 版本适合教学演示，不适合生产环境。建议在 `secure` 版本中优先修复：
1. 密码哈希与登录安全策略。
2. JWT 鉴权与 token 生命周期。
3. CORS 白名单、限流与安全校验。
4. 默认账号与配置安全基线。
